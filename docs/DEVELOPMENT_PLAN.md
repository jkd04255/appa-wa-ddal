## 1. 목적과 제품 원칙

**메인 카피: 같은 집, 조금 다른 세상.**  
**부제: 우리가 몰랐던 서로의 이야기.**

아빠와 10대 딸이 각자 독립적으로 방문할 이유가 있는 두 공간을 제공한다. 아빠 공간은 딸들의 관심 문화·유행을 이해하고 부모로서 고민을 나누는 곳이며, 딸 공간은 뷰티·쇼핑·음식·연예·학교생활·취미 콘텐츠와 또래 커뮤니티를 제공하는 곳이다.

서로의 의견은 **동의를 받은 설문/기고를 편집·집계한 콘텐츠**로만 연결한다. 별도 공간의 게시글 원문을 직접 노출하거나, 원문으로 역추적할 수 있게 하지 않는다.

핵심 원칙: ① 모바일 퍼스트 ② 양쪽의 독립적인 사용 가치 ③ 정중한 상호 이해 ④ 청소년 안전 최우선 ⑤ 출처·확인일·만료일 관리 ⑥ 최소 개인정보 ⑦ 게이트별 점진적 개발.

## 2. 이번에 허용된 개발 범위 / 금지 사항

### 허용: G0 기획 및 G1 정적 UI 시제품

- 역할 선택 랜딩, 아빠 홈, 딸 홈, 트렌드 상세, 각각의 커뮤니티 UI, 서로의 시선을 **한 화면씩** 구현한다.
- 실제 사용자 데이터가 아닌 안전한 합성 샘플을 사용한다.
- 트렌드·설문·세일·게시글이 실제 데이터로 오인되지 않도록 데모 표시를 넣는다.
- 역할 선택과 마지막 공간 기억은 프론트 UI 편의 기능으로 한정한다. 역할 선택만으로 신원·관계·연령을 인증했다고 표시하지 않는다.
- 게시글 작성, 댓글, 투표는 Phase 1에서 필요할 때만 **일회성 시연**한다. 실제 서비스 DB로 전송하지 않는다.

### 금지: 안전 검증 게이트 통과 전까지

- 실사용자 가입/인증, 실게시글·댓글·설문·개인정보 서버 저장, 공개 쓰기 권한
- 청소년 공개 커뮤니티 운영 및 타 공간의 게시물 원문 공개
- DM/1:1 채팅, 사용자 사진 업로드, 위치 기능, 연락처 교환
- 무단 크롤링/콘텐츠 복제, 검증 없는 AI 자동 게시
- 실결제/광고·추천 알고리즘을 통한 청소년 타깃팅, 유료 API 및 임의 배포

## 3. 기술 방향과 설계 유보

- Phase 1 프론트엔드 예정: Next.js + TypeScript + Tailwind CSS
- Phase 2 이후 검토: Supabase PostgreSQL/Auth, RLS 기반 서버 권한
- 배포 후보: Vercel. 배포는 별도 검토와 결정 이후 수행
- 관리자 권한과 일반 계정, 공개 익명 프로필과 비공개 운영 데이터는 분리
- 청소년 대상 서비스의 연령·가입·신고·제재·삭제·보존·운영 프로세스가 검증되기 전 실제 커뮤니티 열람/작성을 공개하지 않는다
- 기술 선택이 확정됐다는 의미가 아니라 단계별 구현/위험 검토의 출발점이다

### 전문가 검토 2 — 웹 개발자 시각 (G0-02)

**구현 가능성과 청소년 안전을 기준으로 수정:** 화면은 작은 PR로 하나씩 만들고 Phase 1에서는 인증/실데이터/운영 기능을 도입하지 않는다.

- 프론트: Next.js App Router + TypeScript + Tailwind는 후보안이다. G1-01에서 의존 버전·lint·typecheck·빌드로 확정한다.
- Phase 1 데이터: 읽기 전용 합성 콘텐츠이며 시연 표시를 붙인다. 시연 입력 글은 서버·DB·외부 분석 도구·브라우저 장기 저장소로 보내지 않는다.
- 트렌드/세일 메타데이터: sourceUrl, publishedAt, verifiedAt, expiresAt, reviewStatus, audience, demo/verified/expired 상태 구분. 확인 불가 세일을 '진행 중'으로 표시하지 않는다.
- 실제 쓰기 권한: 선택된 UI 역할, URL, localStorage는 권한의 근거가 아니다. G2에선 서버 측 권한검사와 RLS, 요청 검증을 모두 적용하며 기본 거부한다. 관리자 비밀키는 서버 전용이다.
- 자기신고식 역할만으로 실제 보호자·청소년 여부를 증명할 수 없다. 적법한 검증 방법과 개인정보 최소 수집 방안이 없으면 '검증된 아빠만 작성' 등의 약속이나 공개 운영을 금지한다.
- 다른 공간의 게시글/댓글/신고 등 민감 원문과, 동의·검토를 거친 '서로의 시선' 편집 집계는 별도 데이터 경계로 분리한다. 소표본 재식별 위험이 있으면 게시하지 않는다.
- XSS·CSRF·스팸·권한 우회·API 직접 접근·비밀키 노출·보존/삭제 정책은 G0-04/G2 검증 대상으로 분리한다.
- G1에는 lint, typecheck, build, 브라우저 및 접근성·모바일 회귀를 적용하고, G2에는 RLS/서버 권한 부정 테스트와 신고 처리 운영 검증을 추가한다.

자세한 아키텍처·데이터 경계·동선: [G0-02 정보구조 및 이중 전문가 검토](./INFORMATION_ARCHITECTURE.md).

## 5. UI/UX 기준

### 랜딩
- "같은 집, 조금 다른 세상." / "우리가 몰랐던 서로의 이야기."
- 아빠로 들어가기 / 딸로 들어가기. 모바일에서 크고 명확한 두 카드
- 마지막 선택 공간으로 재방문, 언제든 랜딩 복귀

### 아빠 공간
- 색상: 아이보리·네이비·웜 그레이, 상대적으로 큰 본문 글자
- 모바일 탭: 홈 / 트렌드 / 커뮤니티 / 서로의 시선
- 홈: 최신 트렌드 5개 → 1분 브리핑 → 아빠 익명 커뮤니티 → 질문·대화 소재
- 각 트렌드 상세에 유행 배경, 공식 콘텐츠 링크, 이해 팁, 비강요형 대화 예시, 날짜·출처

### 딸 공간
- 색상: 크림 화이트·차콜 기반의 절제된 포인트, 사진 중심 매거진 카드
- 모바일 탭: 홈 / 발견 / 커뮤니티 / 서로의 시선
- 주요 주제: 뷰티/올리브영, 패션/쇼핑, 음식/디저트, 아이돌/연예, 숏폼, 학교/공부, 취미
- 딸 공간은 독립적인 방문 가치가 있어야 하며 아빠 콘텐츠를 지나치게 강조하지 않는다
- 세일은 공식 출처·확인일·유효기간이 있을 때만 현재 진행 중으로 표시. 광고/제휴는 별도 표기

### 서로의 시선
- 동일 주제에 아빠/딸의 여러 관점을 비교하되 대표성 오인·고정관념을 경계
- 공개 동의가 없는 게시글, 민감한 개인 사연, 원문/검색 가능한 인용은 사용하지 않음
- 상대 공간과의 DM, 직접 연락, 개인정보 노출 동선을 만들지 않음

### 전문가 검토 1 — 웹 디자이너 시각 (G0-02)

**핵심 전환:** 기능을 홈페이지에 모두 노출하는 '종합 포털'이 아니라, 한 화면에서 다음 행동을 이해할 수 있는 **편집형 매거진 + 커뮤니티 진입 구조**로 설계한다.

- 아빠 홈: 주요 트렌드 1개 + 짧은 카드 4개 + 1분 브리핑 + 커뮤니티 입구 + 서로의 시선 1개. 대화 예시는 상세에 배치하고, 방문자에게 행동을 강요하지 않는다.
- 딸 홈: 사진형 주요 이야기 1개 + 관심사 카테고리 + 발견 피드 + 공식 검증이 필요한 쇼핑 정보 + 커뮤니티. '아빠들의 속마음'을 메인 주제로 과잉 노출하지 않는다.
- 두 공간은 단순한 분홍/파랑 대비가 아니라 **타이포·정보 밀도·사진 비율·편집 리듬**으로 차별화한다. 실제 토큰과 시안은 G0-03에서 결정한다.
- 전체 주요 이동은 각각 4탭. 긴 설명·과도한 캐러셀·중복 CTA는 금지. 카드에는 짧은 문장만, 출처/맥락은 상세에 표시한다.
- G0-03 디자인 완료 기준에 모바일 320/360/375/390/430px, 시스템 글자 확대, 고정탭/안전영역, 44px 권장 터치 영역, WCAG 2.2 AA 수준 대비/포커스를 포함한다.
- 세일, 인기, 응답 통계가 샘플이면 '시연 콘텐츠'로 표시하고 실제 최신 데이터인 것처럼 구성하지 않는다.

상세 근거와 전 화면 목록: [G0-02 정보구조 및 이중 전문가 검토](./INFORMATION_ARCHITECTURE.md).

2. main에는 검증된 문서/코드만 둔다. 모든 변경은 새 작업 브랜치에서 진행한다.
3. 브랜치 예시: docs/g0-02-information-architecture, feat/g1-02-role-landing, fix/...
4. 기능 하나마다 별도 PR을 생성한다. PR에는 범위·변경 파일·테스트 결과·리스크·남은 문제·다음 작업을 기술한다.
5. 동일 PR에서 계획서의 상태 표/변경 이력/테스트 로그를 함께 갱신한다.
6. 문서 G0 작업에는 문서 확인·링크 점검, 코드 G1 작업에는 typecheck/lint/build 및 해당 기능 테스트를 수행한다.
7. 통과 전에는 완료 표시하지 않고, 문제가 있으면 차단 사유와 해결 조건을 적는다.
8. 배포/실사용자 데이터 연결/유료 API는 별도 허가와 안전 조건 없이는 시행하지 않는다.
9. 이전 PR에서 확정한 내용도 후속 검증 결과에 따라 변경 가능하되, 근거와 변경점을 문서에 남긴다.
10. 매 작업 종료 시 **완료 내용 2~3문장 + 다음 단계 1문장 + 단 하나의 ‘다음 단계 진행’ 버튼**을 제공한다. 버튼 클릭으로 다음 사용자 요청을 보내며 이후 단계도 같은 규칙으로 진행한다. 진행 실패는 완료로 표기하지 않는다.

## 7. 공통 완료 기준(Definition of Done)

- 한 번에 하나의 작업 단위만 변경하고 범위 밖 변경을 하지 않았는가?
- 필요한 문서·테스트 로그·변경 이력을 같은 PR에 포함했는가?
- 기존 결정·디자인·기능의 회귀가 없는가?
- 코드 작업 시 lint/typecheck/build와 주요 화면 동작을 확인했는가?
- 모바일 320/375/390/430px에서 가로 넘침/가려짐이 없는가?
- 키보드, 스크린리더, 텍스트 대비 및 포커스 가시성을 고려했는가?
- 모든 합성 트렌드/할인/투표/게시글에 데모 표시가 있는가?
- 접근 키·인증 정보·실사용자 게시글·개인정보가 커밋되지 않았는가?
- PR 검증 근거가 없는데 완료 또는 배포 완료로 표시하지 않았는가?
